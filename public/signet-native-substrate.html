The runtime should be boring.

Signet is a continuity layer, not an inference appliance. Infrastructure work starts when memory, failure, and resource boundaries become explicit.

Signet research note20 August 2026Working direction

There is a version of Signet that is easy to imagine and difficult to ship. It is a single daemon, a generous JavaScript dependency graph, a background memory pipeline, local inference, source watchers, a graph, a database, and a dashboard. It works. It also has a ceiling.

If that daemon can grow toward five gigabytes under load, it is not infrastructure yet. The problem is not that Bun is somehow disqualified. The problem is that the runtime has not made its expensive boundaries legible enough to own.

The compiler is not the boundary.

scriptc makes an interesting offer: ordinary TypeScript can become a small native executable, with a static tier, an explicit dynamic tier, and an FFI surface. That could give Signet a small native control plane, fast tools, and a shared low-level substrate.

But a native addon loaded into Bun still lives inside the Bun process. Compiling code is not the same thing as containing it. If an addon allocates four gigabytes, the daemon still owns the consequence.

Compile where it helps. Isolate where it matters.

Own the adapter, not every engine.

The attractive version of the native-substrate idea is not writing a new database, inference engine, or image library. It is owning a narrow adapter around mature native libraries and exposing only the operations Signet needs.

One C ABI could support a Bun adapter, a scriptc FFI adapter, and an IPC service. The TypeScript layer would keep its current contracts while the implementation becomes more deliberate about allocations, ownership, and lifecycle.

Embeddings become a capability, not a tax.

Built-in ONNX embeddings bring model files, runtimes, platform behavior, and memory costs that do not belong in every edge deployment. Signet already has external paths such as OpenAI-compatible APIs, Ollama, and llama.cpp, as well as an explicit no-embeddings mode.

That means we do not need to recreate ONNX Runtime. We can make embeddings an explicit deployment capability and let the edge profile use SQLite FTS5, graph traversal, structured memory, and provenance-aware source retrieval.

A quiet dependency removal: Signet does not appear to use image processing directly. The current sharp shim exists because Transformers.js imports sharp at package scope. Remove the local embedding stack and sharp likely leaves with it.

The sequence.

This is smaller and more defensible than trying to compile the entire daemon with scriptc. First remove the heavyweight baseline. Then prove one native contract. Then decide which work deserves a process boundary.

01
Drop ONNX

Remove the built-in model, worker, warmup, cache, and runtime assets.

02
Define the ABI

Start with SQLite, vectors, and keyring access.

03
Bind twice

Implement Bun first, then prove scriptc FFI against the same contract.

04
Split heavy work

Use child processes where RSS budgets and restart policy matter.

This is a working direction, not a migration plan.
